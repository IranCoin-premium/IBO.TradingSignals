===================================================================
B) ORDINARY END-USER EXPERIENCE GAPS
===================================================================

1. NO DEMO/TRIAL MODE
   Consider a limited free tier (e.g. one delayed signal per day) so a user can judge
   quality before paying. Flag this as a product decision if it requires backend
   changes beyond simple UI work — do not silently decide subscription pricing/logic
   yourself.

2. RISK DISCLOSURE READABILITY
   The mandatory legal disclaimer text must remain exactly as specified, but pair it
   with a short, plain-language explanation (separate from the legal text, not
   replacing it) so a first-time user actually understands the risk, not just sees a
   wall of legal text they skip.

3. VISIBLE SUPPORT CHANNEL
   Confirm there is an obvious in-app path to real human support (Telegram/WhatsApp/
   email), reachable from Settings without hunting.

4. SUBSCRIPTION/REFUND TERMS ONE TAP AWAY
   Confirm a "اشتراک و بازپرداخت" screen exists and is reachable from Settings,
   matching what PURCHASE_AND_SIGNAL_FLOW.md describes.

5. ONBOARDING FLOW
   Confirm OnboardingTutorialUnitTest.kt corresponds to a real first-run screen sequence
   (notification permission explanation, how to read a signal card, language selection).

6. NOTIFICATION PERMISSION CONTEXT
   Show an in-app explanation of why notifications are needed BEFORE the OS permission
   dialog fires, rather than a bare system prompt with no context.

7. RTL/PERSIAN CONSISTENCY
   Confirm all screens render correctly in RTL layout, including numbers, dates, and any
   charts — check screens beyond the ones with dedicated tests.

8. OFFLINE/CACHED DATA CLARITY
   If FirestoreOfflineCacheManager.kt serves cached signals while offline, the UI must
   clearly mark a signal as "cached/possibly outdated" versus live — presenting a stale
   signal as current could cause a real financial loss for a user acting on it.
